Part 3 · Continuous compliance

The release rule is a file in the repository

# policy.yaml

max_allowed:

  P0: 0

  P1: 0

block_on_any_secret: true

max_failed_controls: 0

Reviewed like code

Changing the rule needs a pull request and an approver.

Enforced on every build

No exceptions by email. The gate returns pass or block.

People own the threshold

AI supplies priorities. It cannot change what is allowed.

AI-Driven DevSecOps · ATAL FDP 2026

Start part three. Compliance usually lives in documents. Policy as code moves the rule into the repository, next to the software it governs. This is the actual policy file from the demo: zero P0, zero P1, no secrets, no failing controls. Three consequences. It has version history, so an auditor can see who relaxed a rule and when. It runs on every build, so there is no gap between the rule and its enforcement. And it separates duties: the model produces priorities, but only a person can change the threshold. In the demo, try changing P1 to 5 live and re-running to show the gate respond.
