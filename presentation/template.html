The problem

Code ships every day.
Security reviews do not.

Attackers already automate. A defence that waits for a person to read every alert loses on speed alone.

Ask the room: how often does project code in your department get a security review? This gap between delivery speed and review speed is why DevSecOps exists, and why AI is being pulled into it.

Part 1 · Intelligent threat detection

Which clients look unlike the rest?

Each dot is one client. Amber = flagged. Red ring = an attacker we planted. Click a dot.

An Isolation Forest scored every client; nobody told it what an attack looks like. First, switch the vertical axis: the data-exfiltration client hides in the crowd on error rate and only stands out on response size, which is why one feature is never enough. Then move the slider: flag more clients and you catch nothing new but add false alarms. That trade-off is the real engineering decision. The logs are synthetic, so the truth is known.

One finding, read two ways

# app/app.py, the /login route query = f"SELECT id FROM users WHERE name = '{username}' AND pw = '{digest}'" row = get_db().execute(query).fetchone()

Scanner severity (Bandit B608)

Medium

It sees a query built from a string. It does not know where the string comes from.

Triage priority, in context

P0: blocks release

The string is a login form field on a public route. No account is needed to exploit it.

Ask the audience what priority they would give before you click. A scanner matches a pattern; a reviewer looks three lines up and sees the input comes from an unauthenticated form. Triage is that step, and it is where a language model earns its place.

Part 3 · Continuous compliance

Controls, checked on every build

Illustrative mapping to OWASP Top 10:2021, NIST SSDF 1.1 and ISO/IEC 27001:2022. A pass means no contradicting evidence in this build. It is not a certificate.

Click a control to see the evidence the pipeline holds for it. Then switch to "Fixed app" and watch every control pass. Compliance becomes a by-product of shipping: each build leaves a dated record of what was checked and decided. Local context: CERT-In's 2022 directions and the DPDP Act 2023 both push organisations towards evidence that is always current.

Part 3 · Continuous compliance

Automate the checking, not the production release

Runs without a person

Scanning every change. Re-checking when a new vulnerability is published. Ranking findings and drafting fixes. Recording control evidence. Deploying to a test environment.

Waits for a person

Releasing to production. Accepting any code or dependency change. Relaxing the policy. Each has a named approver, and the approval is itself compliance evidence.

# new vulnerability or threat, after release Amazon Inspector / GuardDuty finding → EventBridge → Lambda → email to a person

A new vulnerability should reach the right person in minutes, with the evidence attached. It should not rewrite production on its own.

Expect the question "should AI deploy to production?". The answer here is no. Automation makes the decision fast and well-informed; a person still makes it. An approval step with a recorded approver is a change-management control in its own right.

Three things to remember
